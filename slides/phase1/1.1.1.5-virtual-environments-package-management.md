## Why Virtual Environments Matter

**The Problem:**
```bash
# Project A needs requests 2.28.0
# Project B needs requests 2.31.0
# System Python can only have ONE version installed!
```

**The Solution: Virtual Environments**
- Each project gets its own isolated Python environment
- No conflicts between projects
- Clean, reproducible deployments

---

## What is a Virtual Environment?

A **virtual environment** is an isolated Python installation

Think of it as a **sandbox** for your project

**Contains:**
- Python interpreter (links to system Python)
- Independent site-packages directory
- Its own pip
- Isolated from system packages

**Benefits:**
- Project isolation
- Version control
- Clean system Python
- Reproducible builds

---

## Creating a Virtual Environment

```bash
# Create a virtual environment named 'venv'
python -m venv venv

# Create with a different name
python -m venv myproject_env

# Specify Python version (if multiple installed)
python3.11 -m venv venv
```

**What happens:**
- Creates a directory (venv/) with Python installation
- Copies/links Python executable
- Installs pip and setuptools
- Creates activation scripts

---

## Virtual Environment Directory Structure

```
venv/
├── bin/          # (Linux/Mac) Scripts and executables
│   ├── python    # Python interpreter
│   ├── pip       # Package installer
│   └── activate  # Activation script
├── Scripts/      # (Windows) Scripts and executables
│   ├── python.exe
│   ├── pip.exe
│   └── activate.bat
├── lib/          # Installed packages
│   └── python3.x/
│       └── site-packages/
└── pyvenv.cfg    # Configuration file
```

---

## Activating Virtual Environments

```bash
# Linux / Mac
source venv/bin/activate

# Windows (Command Prompt)
venv\Scripts\activate

# Windows (PowerShell)
venv\Scripts\Activate.ps1

# When activated, prompt changes:
(venv) user@machine:~/project$
```

**What activation does:**
- Modifies PATH to use venv's Python
- Updates prompt to show active environment
- Ensures pip installs to venv, not system

---

## Deactivating Virtual Environments

```bash
# From any activated environment
deactivate

# Prompt returns to normal
user@machine:~/project$
```

**Simple as that!**

## Checking Active Environment

## Package Management with pip

```bash
# Install a package
```

## requirements.txt

**The standard way to manage dependencies**

```
# requirements.txt
requests==2.31.0
flask==2.3.3
pandas==2.0.3
numpy>=1.24.0,<2.0.0
```

**Install all requirements:**
```bash
pip install -r requirements.txt
```

**Create requirements file:**
```bash
pip freeze > requirements.txt
```

---

## Version Specifiers

```
# Exact version
requests==2.31.0

# Minimum version
requests>=2.28.0

# Maximum version (exclusive)
requests<3.0.0

# Version range
requests>=2.28.0,<3.0.0

# Compatible release (same major.minor)
requests~=2.31.0  # means >=2.31.0, <2.32.0

# Latest version (not recommended for production!)
requests
```

## Introducing uv: The Fast Package Installer

**uv** is a blazing-fast Python package installer

- Written in Rust
- 10-100x faster than pip
- Drop-in replacement for pip
- Modern dependency resolver

```bash
# Install uv
pip install uv

# Use uv just like pip
uv pip install requests
uv pip install -r requirements.txt
uv pip list
```

---

## pip vs uv: Speed Comparison

```bash
# Installing 50 packages

# With pip:
$ time pip install -r requirements.txt
# ~45 seconds

# With uv:
$ time uv pip install -r requirements.txt  
# ~2 seconds

# 20x faster!
```

**Perfect for:**
- CI/CD pipelines
- Large projects
- Frequent installations
- Development workflows

## uv Commands

```bash
# Install package
uv pip install package-name

# Install from requirements
uv pip install -r requirements.txt

uv pip uninstall package-name

uv pip list

# Freeze requirements
```

## pyproject.toml: The Modern Standard

**PEP 621** - Modern project metadata format

```toml
[project]
name = "my-uipath-agent"
version = "1.0.0"
description = "Document processing agent"
requires-python = ">=3.10"
dependencies = [
    "uipath-sdk>=1.0.0",
    "langchain>=0.1.0",
    "pandas>=2.0.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=7.4.0",
    "black>=23.0.0",
]
```

---

## pyproject.toml vs requirements.txt

**pyproject.toml** (modern):
- ✅ Standard format (PEP 621)
- ✅ Project metadata + dependencies
- ✅ Tool configuration
- ✅ Build system specification
- ✅ Optional dependencies

**requirements.txt** (traditional):
- ✅ Simple and ubiquitous
- ✅ Exact versions (pinned)
- ✅ Works everywhere
- ✅ Generated by pip freeze

**Best practice: Use both!**
- pyproject.toml for source
- requirements.txt for deployment

```bash
# Install with optional dependencies
pip install ".[dev]"

# Install in editable mode (development)
pip install -e .

# With uv (much faster!)
uv pip install .
uv pip install ".[dev]"
```

## Dependency Resolution

**What happens when you install packages:**

1. pip reads your requirements
2. Finds compatible versions
3. Resolves dependencies recursively
4. Checks for conflicts
5. Installs packages

**Conflict example:**
```
Package A requires requests>=2.28.0
Package B requires requests<2.28.0
# CONFLICT! Cannot satisfy both.
```

---

## Handling Dependency Conflicts

```bash
# Conflict error example:
ERROR: Cannot install package-a and package-b because
these package versions have conflicting dependencies.

# Solutions:
# 1. Update packages to compatible versions
pip install --upgrade package-a package-b

# 2. Relax version constraints
# Change requirements.txt from:
requests==2.28.0
# To:
requests>=2.28.0

# 3. Use different packages
# Sometimes packages are incompatible
```

## Lock Files for Reproducibility

```bash
# Create exact snapshot of environment
pip freeze > requirements-lock.txt

# Or with uv (generates uv.lock)
uv lock

# Install from lock file
pip install -r requirements-lock.txt
uv sync
```

**Lock files ensure:**
- Exact same versions everywhere
- Reproducible builds
- No surprises in production

## Real-World Workflow: New Project

```bash
# 1. Create project directory
mkdir my-agent && cd my-agent

# 2. Create virtual environment
python -m venv venv

# 3. Activate
source venv/bin/activate  # Linux/Mac
# or: venv\Scripts\activate  # Windows

# 4. Upgrade pip and install uv
pip install --upgrade pip uv

# 5. Install dependencies
uv pip install uipath-sdk langchain pandas

# 6. Save requirements
uv pip freeze > requirements.txt

# 7. Start coding!
```

## CI/CD with Virtual Environments

```yaml
# Example GitHub Actions workflow
name: Test Agent

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: |
          python -m venv venv
          source venv/bin/activate

          uv pip install -r requirements.txt

      - name: Run tests
        run: |
          source venv/bin/activate
          pytest tests/
```

## Troubleshooting Common Issues

**Issue: "pip not found" after activation**
```bash
# Solution: Reinstall virtualenv
python -m venv --clear venv
```

**Issue: Permission denied on Windows**
```bash
# Solution: Allow script execution
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

**Issue: Wrong Python version in venv**
```bash
# Solution: Specify Python explicitly
python3.11 -m venv venv
```

## Docker and Virtual Environments

```dockerfile
# Dockerfile for UiPath Agent
FROM python:3.11-slim

WORKDIR /app

# Copy requirements
COPY requirements.txt .

# Install dependencies (no venv needed in container!)
RUN pip install --no-cache-dir -r requirements.txt

# Copy application
COPY src/ ./src/

CMD ["python", "src/agent.py"]
```

**Note:** Virtual environments unnecessary in containers—the container IS isolated!

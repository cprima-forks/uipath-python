## Organizations

**Top-level container**

- Represents your entire company
- Contains one or more tenants
- Managed via UiPath Cloud Portal
- Billing and licensing at this level

**Example:**
- Organization: "Acme Corp"
  - Multiple tenants for different divisions

---

## Tenants

**Isolated workspaces within an organization**

**Key characteristics:**
- Complete data isolation
- Separate users and permissions
- Independent robots, processes, assets
- Own database (logical separation)

**Use cases:**
- Separate business units (Finance, HR, Sales)
- Isolate prod from non-prod
- Multi-client scenarios (for service providers)

**Think: Each tenant is a completely separate Orchestrator instance**

---

## Folders

**Organizational units within a tenant**

**Key characteristics:**
- Organize resources by department, project, or environment
- Share tenant-level resources
- Fine-grained access control
- Can see other folders (with permissions)

**Use cases:**
- Departments: HR-Folder, Finance-Folder
- Environments: Dev-Folder, Staging-Folder, Prod-Folder
- Projects: Project-A, Project-B

**Think: Folders are like subdirectories in a file system**

---

## Tenant vs Folder: When to Use Which

**Use Separate Tenants For:**
- ✅ Complete data isolation required
- ✅ Different business units with no data sharing
- ✅ Multi-client scenarios
- ✅ Different security domains

**Use Folders Within Tenant For:**
- ✅ Same organization, different teams
- ✅ Different environments (Dev/Test/Prod)
- ✅ Project-based organization
- ✅ Shared resources needed

**Rule of thumb**: If they should NEVER see each other's data → Tenants. If they might share some resources → Folders.

## Robots

**Execution agents that run automations**

**Two main types:**

**Unattended Robots**
- Run autonomously without human supervision
- Triggered by schedules or queues
- Run on dedicated machines or VMs
- For back-office automation

**Attended Robots**
- Work alongside humans
- Started manually by user
- Run on user's workstation
- For front-office automation

---

## Robot Types Comparison

| Feature | Unattended | Attended |
|---------|-----------|----------|
| **User Presence** | Not required | Required |
| **Trigger** | Schedule/Queue | Manual start |
| **Machine** | Dedicated | User workstation |
| **Use Case** | Back-office | Front-office |
| **Scaling** | Easy (add machines) | Limited (users) |
| **Cost** | Higher licensing | Lower licensing |

## Processes

**Deployed automation workflows**

**Lifecycle:**

1. **Develop** in Studio
2. **Publish** to Orchestrator
3. **Deploy** to folder(s)
4. **Assign** to robots
5. **Execute** via trigger

**A process package contains:**
- Compiled workflow (`.nupkg` file)
- Dependencies
- Version information

**Can deploy different versions to different folders (e.g., v1.0 in Prod, v2.0 in Test)**

---

## Queues

**Work distribution mechanism**

**How they work:**
1. Producer adds items to queue
2. Consumer robots pull items
3. Process items independently
4. Report success/failure

**Benefits:**
- Load balancing across robots
- Automatic retry logic
- Transaction handling
- Priority management

**Example:** 1000 invoices → Queue → 10 robots process concurrently

---

## Queue States

**Queue Item Lifecycle:**

```
New
  ↓
In Progress (Robot processing)
  ↓
Success ✓  or  Failed ✗
               ↓
          Retry (up to max retries)
               ↓
          Failed (final)
```

**Queue items can be:**
- **New**: Waiting to be processed
- **In Progress**: Currently being processed
- **Successful**: Completed successfully
- **Failed**: Failed processing (after retries)

## Assets

**Configuration values and credentials**

**Asset Types:**

**Text**: String values (URLs, file paths)
**Bool**: True/False flags
**Integer**: Numeric values
**Credential**: Username/password pairs

**Key features:**
- Environment-specific (different values per folder)
- Centrally managed
- Updated without redeploying processes
- Credentials are encrypted

---

## Assets Example

**Development Folder:**
```
API_URL = "https://api-test.example.com"
MAX_RETRIES = 5
ENABLE_DEBUG = True
DB_CREDENTIALS = test_user / test_pass
```

**Production Folder:**
```
API_URL = "https://api.example.com"
MAX_RETRIES = 3
ENABLE_DEBUG = False
DB_CREDENTIALS = prod_user / prod_pass
```

**Same process, different asset values!**

## Best Practices: Robot Organization

**Do:**
- ✅ Name robots descriptively (FINANCE-BOT-01)
- ✅ Use machine templates for consistency
- ✅ Group by function or location
- ✅ Monitor robot health regularly

**Don't:**
- ❌ Use generic names (Robot1, Robot2)
- ❌ Mix unattended and attended on same machine
- ❌ Over-provision (unused robots cost money)

---

## Best Practices: Process Management

**Do:**
- ✅ Use semantic versioning (1.0.0, 1.1.0, 2.0.0)
- ✅ Test in lower environments first
- ✅ Document process dependencies
- ✅ Clean up old versions

**Don't:**
- ❌ Deploy untested code to production
- ❌ Skip version numbers
- ❌ Leave hundreds of old versions

---

## Best Practices: Queue Design

**Do:**
- ✅ Keep queue items focused (one invoice per item)
- ✅ Set appropriate priorities
- ✅ Configure reasonable retry counts
- ✅ Monitor queue backlog

**Don't:**
- ❌ Put huge data in queue items (use references)
- ❌ Set infinite retries
- ❌ Let queues grow unbounded

---

## Best Practices: Asset Management

**Do:**
- ✅ Use assets for environment-specific values
- ✅ Name assets clearly (API_URL not URL1)
- ✅ Document asset purpose
- ✅ Rotate credentials regularly

**Don't:**
- ❌ Hard-code values in workflows
- ❌ Store secrets in process code
- ❌ Use same credentials across environments

## Common Orchestrator Patterns

**Pattern 1: REFramework + Queue**
- Dispatcher process adds items to queue
- Performer processes pull and process items
- Scalable, resilient

**Pattern 2: Scheduled Batch Processing**
- Process runs on schedule (nightly)
- Processes batch of records
- Sends summary email

**Pattern 3: Event-Driven**
- External system triggers process via API
- Process executes on-demand
- Returns result to caller

## Troubleshooting Common Issues

**Robot Disconnected:**
- Check network connection
- Verify robot service running
- Check license allocation

**Process Won't Start:**
- Verify process deployed to folder
- Check robot has access to folder
- Verify robot available (not busy)

**Queue Items Stuck:**
- Check for abandoned transactions
- Verify robots assigned to queue
- Check for errors in logs
